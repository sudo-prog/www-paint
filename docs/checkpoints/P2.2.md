# P2.2 — Layer-aware generation, scoring & paint order

**Date:** 2026-11-11 · Agent: BE (ThinkPad) · Status: **partial — see §4**

---

## 1. Goal (roadmap 2.2)

> Layer-aware generation, scoring, paint order — *different style per layer on
> one image*.

## 2. Research / design

The renderer dispatches each shape on **its own** `shape.style`
(`Renderer.drawShapeAt` → `this._styles[shape.style]`). A `layer.style` field
alone is therefore inert. Two consequences the codebase already carried:

- `app.js`'s `layer-style-change` handler set `layer.style` and did nothing
  else — a comment there called the style dropdown a no-op until regenerate.
- Multi-layer generation assigned shapes to tonal bands
  (`background / shadows / outline / midtone / highlights`) but had no way to
  give a band its own style.

So 2.2 needs two pure operations plus one live-apply method:

| Piece | What it does |
|---|---|
| `resolveLayerStyles(spec)` | normalise `undefined` / `'ink'` / `{band:style}` / `Map` → `Record\|null`; `null` = no-op so non-opted-in callers stay byte-identical |
| `applyLayerStyles(shapes, spec)` | restamp each shape's `.style` by its band (`layerName`, else numeric `layer`) |
| `preserveLayerProps(fresh, prev)` | carry `visible/opacity/blendMode/style/locked` across a regenerate by `_name` |
| `engine.setLayerStyle(id, style)` | set `layer.style` **and** restamp the layer's existing strokes, so the change renders immediately |

New module `js/engine/layer-styles.js` (pure, node-testable). Wired into
`engine.generate()` (both the worker and Painter paths) and `app.js`'s
`layer-style-change` handler.

## 3. Result — what works and is verified

- `node tests/engine.test.js` → **63/63** (10 new layer-styles tests), `node
  scripts/visual-regression.cjs` → **pass=9 fail=0 error=0** (baselines unmoved —
  the new option defaults to a no-op).
- `scripts/layer-styles-probe.cjs` (real headless Chromium, index.html):

  ```
  PASS: setLayerStyle applies live (ink 25564->25600), per-layer mapping + preserve correct
  ```

  i.e. `generate({style:'watercolor'})` → render hash H1; `setLayerStyle(0,'ink')`
  → strokes all restamped to `'ink'`, render hash H2 ≠ H1, and re-rendering is
  stable (H3 == H2). `resolveLayerStyles`/`applyLayerStyles`/`preserveLayerProps`
  behave as specified.

- **Crash fixed.** `_initMultiLayerLayers()` referenced an undefined `Engine`
  (the class is `PaintingEngine`) → `ReferenceError` on every multi-layer
  generate. Fixed to `PaintingEngine.LAYER_NAMES`.

## 4. ⚠ Known defect — the multi-layer RENDER path is broken (not fixed here)

Evidence from the probe while exercising multi-layer mode (`multiLayer:true`):

1. The `Engine` ReferenceError above proves multi-layer generation had **never
   run** in the app (`multiLayer` defaults to `false`).
2. With it fixed, `renderer.renderAll()`'s multi-layer branch renders only the
   **first** layer's offscreen canvas; every subsequent layer canvas is empty
   (`layerInk: { background: 27809, shadows: 0, outline: 0, midtone: 0 }`).
   Consequence: per-layer visibility/opacity/blend on layers after the first
   have no effect on the composite (hiding the top `highlights` layer left the
   render hash unchanged).

So *"different style per layer on one image"* through the tonal-band model is
**not** achievable yet: the plumbing (`layerStyles`, `preserveLayerProps`) is in
place and tested, but the composite must be repaired first. That repair is a
separate, well-scoped BE task on `js/engine/renderer.js` — it is out of scope
for this checkpoint, which deliberately does not claim it.

**Also observed (needs a follow-up check, not a claim):** in a *bare* engine
(constructed directly, no app shell) the `pencil` style drew **0 ink** on the
plain canvas while `watercolor`/`ink` drew normally. The project's own
`--disable-gpu` harness renders `pencil` fine, so this is either a bare-engine
harness artifact or a real style/seed issue (`_convertShape` stamps
`seed: this._seed`, a number, onto every shape). Recorded here to investigate
against the official harness before drawing a conclusion.

## 1. Research

Phase 3 asks for a *lightweight* wetness/pigment model so watercolor and ink
can bleed, pool and dry. The design constraint is that it must run in the
existing static, buildless app on a 2D canvas — so the model has to be a small
explicit grid simulation, not a fluid solver.

### 1.1 What public sources actually do

| Source | Idea taken | How it is expressed here |
|---|---|---|
| **inkwash** (johnowhitaker) | Ink moves only where paper is wet; a wetness grid gates transport | `wetness` gates pigment transport; a cell with no water cannot move pigment |
| **watercolor-playground** (msurguy) | Wet-gated flow plus tide lines (darker rim at a drying wash boundary) | Pigment concentrates at the wet/dry front because transport only happens where `wetness > 0` |
| **dli/paint** | Keep colour separate from height/wetness; derive shading from the height field | `pigment`/`fixed` channels are independent of `paperHeight`; `compositeInto` derives the wet sheen from `wetness` |
| **wet-paint-flow** | Height + wetness + bristle channels | `paperHeight` field + `wetness` + per-channel pigment |

### 1.2 Technique root

The governing paper is **Curtis, Anderson, Seims, Fleischer, Salesin,
"Computer-Generated Watercolor" (SIGGRAPH 1997)**. Its three-layer model is
the right shape for a 2D grid:

1. **Shallow-water layer** — water flows across the paper surface and
   carries pigment with it.
2. **Capillary layer** — paper absorbs water; this is what makes a wash
   *dry* rather than sitting on the surface forever.
3. **Pigment layer** — pigment is deposited when water evaporates; granulation
   is pigment settling into the paper's tooth.

The full Curtis model runs a shallow-water PDE. That is too heavy for the
check path here (no build step, no new dependency, must be node-testable on
plain buffers), so the implementation uses a **relaxation approximation**:
water moves toward the paper's capillary capacity and pigment is advected
along the resulting wetness gradient. This keeps the *behaviour* (bleed, pool,
dry, granulate) while dropping the PDE solver.

### 1.3 What "lightweight" means here

- One `Float32Array` per scalar field: `wetness`, `paperHeight`, `capacity`,
  plus `pigment`/`fixed` as `n*3` for RGB.
- No WebGL, no DOM, no canvas in the core. `compositeInto` is the only place a
  2D context is touched, and `toRGBA()` provides a node-safe equivalent.
- One dependency: `js/utils/rng.js` (`createRNG`) — the project's own seeded
  mulberry32. No `Math.random()` anywhere.

## 2. Design

### 2.1 Fields

| Field | Type | Meaning |
|---|---|---|
| `wetness` | `Float32Array(n)` | Water held at each pixel. 0 = dry. |
| `paperHeight` | `Float32Array(n)` | Paper surface relief above the base plane. IF-2 calls this `height`; the grid dimension is also `height`, so the field is exported as `paperHeight` and the grid dimension stays `height`. |
| `pigment` | `Float32Array(n*3)` | Mobile pigment mass per RGB channel. |
| `fixed` | `Float32Array(n*3)` | Pigment fixed into the paper (immobile). |
| `capacity` | `Float32Array(n)` | Capillary capacity = `CAPILLARY_K * paperHeight`. |

Pigment **mass** is `pigment[3i]+pigment[3i+1]+pigment[3i+2]`. Total mass =
mobile + fixed. That total is the conservation target.

### 2.2 Step order in `dry(dt)`

1. **Relax water** toward `capacity`. Excess (free surface water) sheds;
   water below capacity wicks up — but wicking is **disabled while drying**,
   otherwise evaporation can never win and the frame never dries.
2. **Transport pigment** along the wetness gradient. For each cell, the
   gradient `(gx, gy)` of `wetness` is computed from neighbours; a fraction
   `k = flowRate * dt * 0.25 * min(1, wetness)` of the mobile pigment leaves
   toward the *drier* neighbour(s). The split between axes is proportional to
   the gradient components, so a purely 1-D gradient sends everything one way.
3. **Evaporate**. Free water (above capacity) evaporates fast; held water
   evaporates slowly. Water bookkeeping only — no pigment is destroyed.
4. **Fix pigment**. Where total pigment load ≤ `pigmentCapacity * (1 +
   capacity)`, a fraction `fixRate * dt` moves from `pigment` to `fixed`.

### 2.3 Why mass is conserved

- `deposit` only *adds* pigment.
- Transport moves pigment between cells and through a scratch buffer that is
  summed back — nothing is dropped.
- Evaporation touches `wetness`/`waterLayer` only.
- Fixing moves pigment from `pigment` to `fixed`; the sum is unchanged.

The only accumulation error is Float32 rounding, measured at **< 3e-8
relative** over 40 s of simulated time with transport enabled.

### 2.4 Determinism

- The paper relief is a fixed sine lattice shifted by a seeded offset
  (`offX`, `offY` from `createRNG(seed)`), plus optional seeded granulation.
- No per-pixel randomness in `deposit` (soft quadratic falloff is analytic).
- No `Math.random()`, no time-based input, no call-order dependence in the
  transport math (gradients come from the current state).

### 2.5 Interface notes / deviations from IF-2

IF-2 specifies `height: Float32Array`. The constructor also needs a grid
height, so both are exported:

```js
createWetSim(width, height, opts)
//   -> { width, height, wetness, paperHeight, pigment, fixed, ... }
```

`paperHeight` is the IF-2 `height` field. This keeps the frozen shape
readable while avoiding a duplicate key. **`compositeInto(ctx)` requires
`ctx.canvas.width/height === sim grid`** — it throws on mismatch, which is the
honest failure rather than a silent resize.

`toRGBA(opts)` is an additive convenience for node-safe rendering (used by the
browser probe and available for debug views); it is not required by IF-2.

### 3.3 Integration

`renderer.js` is **ThinkPad-owned** (HANDOFF §6), so it was *not* edited. The
exact call site is documented in `js/engine/wetsim.js` (header, "Integration
contract") and summarised here:

```js
import { createWetSim } from './wetsim.js';
// constructor:
this._wetSim = opts.wetMedia ? createWetSim(this.width, this.height, opts.wetMedia) : null;
// renderLayer(), after the style draw, before ctx.restore():
if (this._wetSim) { this._wetSim.dry(opts.dt || 1/60); this._wetSim.compositeInto(ctx); }
// style draw hook, per stroke:
this._wetSim?.deposit(shape.x, shape.y, shape.size, shape.color, { amount, water });
```

Construct the sim at the **render target's** size (see the mismatch check in
§2.5). Defaults keep the current path byte-identical: `opts.wetMedia` is unset
unless a style opts in, so no existing style changes output and the 9 pinned
baselines do not move.

### 3.6 Known limits

- Transport is a gradient-relaxation approximation, not a shallow-water PDE;
  it bleeds and pools but does not simulate true flow momentum or pooling in
  depressions beyond what `capacity` encodes.
- `compositeInto` paints the whole frame each call (one `ImageData`). At 512×512
  that is ~1 MB per frame — acceptable for a per-stroke reveal, not for
  continuous animation.
- Pigment is RGB, not spectral; colour mixing is additive-mass, so two
  complementary washes darken rather than producing a subtractive neutral.

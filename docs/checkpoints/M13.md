# Checkpoint M13 — a11y + responsive sweep

**Date:** 2026-11-13 · Agent: Mac / AIR HERMES · Stream **M13** (`docs/MAC-TASKS.md` Round 3)
**Goal:** every interactive control keyboard operable, visible focus, ≥ 44×44; overlays `role=dialog`/`aria-modal`/Escape/focus-restore; `prefers-reduced-motion`; 390 → 1920 with no clipped or overlapping chrome · **Status:** delivered

---

## 1. What "the a11y bar" means here

`docs/MAC-TASKS.md` M13 exit criteria, restated as measurable checks:

| # | Criterion | Measured by |
|---|---|---|
| A | Keyboard operable | every control is a real focusable element (`button`/`input`/`select`/`textarea`/`a[href]`) |
| B | Visible focus | a `:focus-visible` rule with a 2px accent outline + ring, and no control-specific rule that removes it |
| C | ≥ 44×44 | `getBoundingClientRect()` on every visible control, at every width |
| D | Accessible name | `aria-label` / `aria-labelledby` / `<label for>` / text content |
| E | Overlays | `role=dialog` + `aria-modal`, Escape closes, focus moves in, focus returns to the trigger |
| F | Live regions | `role=status` / `aria-live=polite` on status surfaces |
| G | Reduced motion | a `prefers-reduced-motion` block that kills animations and transitions |
| H | Responsive | no document horizontal overflow, no off-viewport control, no clipped control |

Harness: **`scripts/a11y-sweep.cjs`** (NEW). It runs three passes per width —
as-found, every-overlay-open, and each left-rail panel in its own open state
(the rail is exclusive, so a panel measured while a sibling occupies it is
translated off-screen and would report a false failure). JSON →
`docs/research/a11y-sweep.json`; screenshots → `docs/research/a11y/<width>.png`.

## 2b. Why the first `underMin 0` was wrong (found 2026-11-14)

The first M13 run reported `underMin 0` at every width. It was not a
measurement — it was a **probe artifact**:

- The sweep's `allOpen` pass clicks every toggle, including `toggle-layers`.
- `toggle-layers` is a **desktop-only collapse toggle** (`js/ui/app.js:449` →
  `_setPanelCollapsed`, which sets `is-collapsed` above 768px and
  `panel--mobile-closed` below it).
- On desktop the `allOpen` pass therefore **collapsed the layers rail**, and
  every layer control measured `0x0`. The audit's visibility filter skips
  zero-area elements, so the check passed vacuously.
- The real rows were still **32x32**: `layer-visibility-btn`,
  `layer-action-btn` ×3, `layer-style-select`, `layer-opacity-input`
  (6 unique controls, 12 instances per width at 390/500/768).

Fix, in two parts:

1. **CSS** (§3.7 below) — the row's controls are raised to a real 44px box.
2. **Probe** — `PAGE_AUDIT_LAYERS` opens the rail by the viewport's own
   mechanism (`toggle-layers` on mobile, `is-collapsed` removal on desktop),
   asserts `rowWidth > 0` before measuring, and reports `layersRailOpen` /
   `layersRailRowWidth` in the summary. The layers subset is re-derived inside
   the page (a DOM node cannot cross the Playwright boundary) and scoped to
   `.panel--layers`, so the brush panel's deliberately-10px slider rows are not
   misreported as layer defects.

The Maestro flows gained the same assertion (§4.2), so both harnesses now cover
it.

The `noFocusRule` column in the raw JSON reads 29/16 — that is the probe's own
terminology for "covered by the global `:focus-visible` rule rather than an
element-specific one", which is compliant. `focusRemoved` (a control whose own
rule kills the ring without replacing it) is **0**.

### 2c. A pixel-measurement trap worth recording (slider thumbs)

Raising the sliders to a 44px box made the **thumb** look wrong in screenshots:
`.layer-opacity-input` measured a ~11×7.5 css px disc against its 44px box,
while the M13-approved `.slider-row input[type=range]` thumb measured ~12×6 css
px against the same box.

**Both are the same artifact.** A control — a bare `<input type="range">` with
`::-webkit-slider-thumb { width: 24px; height: 24px }` and no app CSS at all —
renders a **7×19 css px** disc in this headless Chromium. So `getComputedStyle`
and pixel measurement of `::-webkit-slider-thumb` in headless Chromium report a
disc far smaller than the declared size; the CSS is correct and the control is
correct. **Do not "fix" a slider thumb from a headless screenshot** — the
`.slider-row` sliders M13 already approved measure identically. (A real defect
here would show the thumb *missing*, or the *track* misdrawn; the track is
verified: a 3px line at the vertical centre of the 44px box.)

## 3. Defects found and fixed

Each was found by the sweep, then reproduced in isolation before fixing.

### 3.1 Four controls had no accessible name

The paint toolbar's `<label>` elements in `index.html` have **no `for`
attribute**, so the label text is not associated with its control:

- `#paint-preset` (select), `#paint-color` (colour input), `#paint-weight` (range)
- `.layer-opacity-input` (the layers panel's opacity slider; its row has no label at all)

`index.html` and `js/ui/app.js` are ThinkPad-owned, so the fix is **not** in
those files. `js/ui/a11y-hardening.js` adds the `aria-label` at runtime, and
`js/ui/layers.js` (Mac-owned) sets it at creation. A probe that asserts
`aria-label !== null` passes on both.

**A trap found while fixing this:** my first `accessibleName()` helper treated
an input's `value` as its name. That made the helper believe `#paint-color`
("#222222") and `#paint-weight` ("4") already had names, so the fix silently
skipped exactly the controls it was written for. Removed; the browser does not
use `value` as an accessible name either.

### 3.2 Every control was below the 44px floor

`--touch` was 32px (desktop) / 32px (mobile) and `--touch-sm` was 28px/24px,
so **no** control reached 44px. The nav buttons were 40×40, the round top-bar
buttons 32×32, the collapse chevrons 24×24, the layer-row icon buttons 24×24,
and every slider was 3px tall (the thumb is a pseudo-element and is not part
of the element's box).

Fix: a new `--touch-a11y: 44px` token applied to every interactive control, and
slider rows (`--touch-a11y-sm` → the row/thumb band) raised to 44px so the
tappable area is real, not just the track.

### 3.3 The first CSS pass silently did nothing

The M13 block was appended, but a later same-specificity rule won the cascade:
`.top-bar__center .nav-btn` (specificity 0,2,0) overrode the bare `.nav-btn`
rule, and `.form-input:focus` overrode `.form-input`. The block was moved to
the end of the file **and** the selectors were given the specificity needed to
land. Verified by re-measuring — the first attempt measured 40×40 nav buttons
after the "fix".

**Lesson:** an accessibility rule appended to a 2900-line stylesheet is not
applied until a probe confirms the computed value changed.

### 3.4 A closed/hidden rail panel was still in the tab order

`.panel--media.panel--hidden` and `.panel--library.panel--hidden` set
`display: flex` (to keep the mobile layout), and `.panel--mobile-closed` only
applies a `transform`. Either way the panel's controls remained **visible to
the a11y tree and reachable by Tab** while the panel was off-screen.

Fix: the closed and hidden rail states also get `visibility: hidden`, which
removes them from the a11y tree and the tab order without touching the
transform.

### 3.5 The 390px top bar overflowed the viewport

Six 44px nav buttons + gaps = 284px, plus the right-side group. The bar had a
fixed 40px height, so the right-side buttons wrapped to a second line **below
the header** and off-screen (`top-bar__right` measured `y: -2.5 … bottom: 41.5`
with a 40px header; later `right: 512px` in a 390px viewport).

Fix: the bar wraps and grows, `--header-h` is overridden to 111px at
`max-width: 768px` (the mobile panels are pinned to `top: var(--header-h)`), and
the nav buttons get a 44px min-width.

### 3.6 Sliders had no focus ring

`.slider-row input[type="range"]`, `.layer-opacity-input`, `.form-range`,
`.paint-toolbar__slider` and `.motion-scrubber` all set `outline: none`. A
class selector outranks the bare `:focus-visible` rule, so keyboard focus on
every slider was invisible.

Fix: explicit `:focus-visible` rules on each slider control, with a 2px accent
outline.

### 3.7 The 250px layers rail could not fit 44px buttons

After §3.2, four 44px layer-row buttons plus the row padding overflowed the
250px rail by 2px at 1024/1440 (`layer-row__main` and a delete button measured
`right: 1026` in a 1024px viewport).

**First attempt (wrong):** the row's own buttons were pinned to 32px, recorded
as a "deliberate exception" in §6. That exception was itself wrong — it left
six controls below the brief's 44px bar, and the sweep did not catch it because
of the `allOpen` collapse artifact described in §2b.

**Fix (2026-11-14):** every row control gets a real 44px box and the row
**wraps**. The row is 231px at 1024 and 242px at 1440, so four 44px controls
cannot share one line (4×44 + 3×4 = 188, leaving 43/54px for the drag handle +
name) — the name is the only element allowed to shrink, and it keeps its 74px
floor so "Layer 1" is never truncated (`min-width: 74px`, `flex: 1`). Measured:
rows 44×44, no overflow, no clipping, name untruncated at every width.

**Two writers landed this independently and both are correct.** The Mac wrote
`css/style.css` §13 first (44px boxes + `.layer-row { display: block }` +
`flex-wrap` on `.layer-row__main`), then the ThinkPad's Syncthing copy overwrote
the file at 04:16 with its own equivalent block (44px boxes + `flex-wrap` on
`.layer-row__main, .layer-tools-row`, no `display: block`). **Both produce the
same measured result** — `underMin 0`, rows 44×44, no overflow — and the current
file is the BE version. Recorded here because a one-writer-per-file hazard is
real on this repo; the final state is verified, not assumed.

Scoped to the row's controls only — the panel-head collapse button and the
Add-layer button were already 44px and are untouched.

### 3.8 Modal focus restore was incomplete

Three overlays; two ThinkPad-owned. `#export-root` (export dialog) and
`#settings-overlay` moved focus **in** but never put it back; `#export-panel-root`
restored on click-close but not on Escape.

Fixes, all in `js/ui/a11y-hardening.js` (no ThinkPad file edited):

- A document-level capture-phase keydown handler restores focus after Escape.
- A `focusin` handler on `document.body` catches the "modal closed while focus
  was inside it" case (Chromium does not fire `focusin` on BODY when focus is
  *lost*, so this alone was not enough).
- `window.__UISettings.show()` / `.hide()` are wrapped — the settings overlay is
  created lazily by `_UISettings.show()`, so no click listener can observe the
  trigger before the root exists. The wrapper records `document.activeElement`
  at show time and restores it at hide time.

**Two traps on the way:**
1. `setTimeout(0)` and `requestAnimationFrame` both ran before the lazy overlay
   existed. Wrapping the singleton's `show()`/`hide()` is the only reliable
   anchor.
2. `root` was captured once at wrap time. When the overlay is re-created the
   cached reference silently stops working. The code now resolves
   `document.getElementById(spec.id)` at every call.

3. **`evalScript` with a multi-line block works; a `${...}` shorthand does not
   accept a statement block.** Use the `|` block form.

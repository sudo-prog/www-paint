## 3. Design

Two halves, both pure and node-testable.

**`metrics.js` — the comparison.** A comparison between two `RefPacket`s is only
meaningful if both sides use the same feature definitions, so the render is
rasterised with the harness's own rasteriser and then analysed by the *same*
analyser the reference went through. No second feature extractor was written.

| Term | Weight | Measure |
|---|---|---|
| `scale` | 0.30 | L1/2 distance between the stroke-scale histograms, as distributions |
| `orientation` | 0.25 | `1 − orientationMatch`: `cos(2·Δθ)` kernel over the 12 bins |
| `coverage` | 0.20 | L1/2 between tonal-band occupancy |
| `bandScale` | 0.15 | mean absolute difference of `strokeScaleByBand` |
| `coherence` | 0.10 | difference of mean structure-tensor anisotropy |

The orientation kernel is the one real design decision. The packet's bins span
**[0, PI)** — a tangent has no arrowhead, so θ and θ+PI are the same line — which
makes `cos(2·Δθ)` the correct rotation-aware comparison: parallel = +1, 45° = 0,
90° = −1. Bin *i* against bin *i−1* (the wrap) compares correctly for free,
because a cosine is even and 2π-periodic. A plain L1 over `min(s, roll(s))` would
have been wrong: it treats a 90° rotation as free.

**`score.js` — `scoreProfileStyle(profile, image, reference, opts)`** renders the
profile on `image`, rasterises, analyses the render, and scores it against the
reference packet. `composite = styleWeight·styleMatch + (1−styleWeight)·simMae/100`
(default `styleWeight` 0.7: the style term dominates, but fidelity stays in the
loop so a profile cannot "win" by painting something unrelated).

**`gate.js` — guards.** `gateChange` could already require a mean gain with no
per-image regression *on one objective*. S2 needs a second constraint (keep a
style gain only if fidelity held), so `guards: [{ metric, maxDrop }]` was added.
It is additive: `GATE_DEFAULTS.guards = []`, so every existing call behaves
exactly as before (asserted).

## 4. Evidence — unit tests

```
$ node tests/engine.test.js
Passed: 131   Failed: 0      (was 123; +8 S2 tests)
```

The eight tests are deliberately **structural**: identical packets are 0 in every
term; each term moves the composite by exactly its own weight (orientation 90° →
`0.25 × 1`; half the scale mass moved → `0.30 × 0.5`); the metric is symmetric,
deterministic, bounded, and throws on a missing packet; `scoreProfileStyle` is
bit-deterministic across runs, honours the stroke budget, mixes the composite
exactly (`styleWeight` 1 → `composite == styleMatch`, 0 → `composite == simMae/100`),
and a different reference changes the score; the gate reverts a style gain bought
with a fidelity drop and stays `pending` without a guard.

**No test asserts that style-match improves on a synthetic image.** A synthetic
target may back a structural claim; a *fidelity* claim has to be measured on real
images, which is what §5 is for.

## 6. Honest assessment of that measurement

- **The direction is right and it is reproducible, but the margin is small
  (+0.0027).** Two reasons, both worth writing down rather than hiding:
  1. **The two references are renders of the SAME content** (the harness's fixed
     test composition), so their S1 packets are dominated by the content they
     share: the scale histograms are `[0,0,0,0,8,8,8,97]` vs `[0,0,0,0,5,7,7,102]`.
     This is a *weak* pair to discriminate on, not a broken metric.
  2. **The `orientation` term sits at ≈0.50 for both references** — a coin flip,
     and it carries the largest single weight (0.25). Almost all of the small
     margin comes from `scale` and `coherence` instead. A term that reads 0.5
     regardless of the reference is not earning its weight, and the reason is not
     yet known: candidates are (a) the render's raster genuinely sits ~45° away
     from the reference's dominant direction, (b) the tangent convention differs
     between what the painter emits and what the analyser measures, (c) both
     packets are near-uniform in orientation because a 700-stroke render spreads
     across all directions. **This is the first thing S9/S3 should look at.**
- **A stronger reference pair is needed to call the metric validated.** Two
  genuinely different *style* images (not two renders of one composition) are the
  right test, and that needs references the repo does not have yet — a Track-S S3
  (multi-reference) job.
- The measured `styleMatch` is therefore reported as *"mechanism done, direction
  confirmed, magnitude not yet meaningful"*. `docs/ROADMAP_STATUS.md` says exactly
  that; do not upgrade it to "validated" without a stronger pair.

## 9. Hand-off notes

- `scoreProfile` (fidelity) and `scoreProfileStyle` (style) are separate entry
  points on purpose. Do not fold style terms into `scoreProfile` — every existing
  baseline, bench number and gate result was produced by that function, and a
  changed objective silently re-ranks all of them.
- `propose.searchProfile` drives `scoreProfile`. Pointing it at style match is a
  one-line change (`scoreProfileStyle` with a fixed reference packet) but it is
  **not done here** — it needs the stronger reference pair from §6 to be worth
  measuring, and it belongs with S9.
- S2's `guards` are generic: any future two-objective change (e.g. "raise SSIM
  without dropping `simMae`") reuses them.

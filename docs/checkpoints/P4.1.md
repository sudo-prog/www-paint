# Checkpoint P4.1 — the engine consumes a Style Profile

**Date:** 2026-11-12 · Agent: BE (ThinkPad) · **Status: done** · Roadmap Phase 4.1

---

## 1. Goal

Phase 4.1 (roadmap §5, `docs/STYLE_PROFILE.md`): *the engine consumes the full
Style Profile.* The profile is WWW_PAINT's single portable object — the thing the
AI loop (Phase 5) proposes, the library UI (4.2) saves and loads, and the LAYERS
integration wraps. Until now the schema was frozen but nothing *read* it.

## 2. Design — `js/engine/profile.js` (new, pure, node-testable)

A dependency-free, deterministic reader — no DOM, no canvas, no randomness:

| Export | Role |
|---|---|
| `validateProfile(profile)` | draft-07 **subset** validator → `{ok, errors:[{path,message}]}`. Covers exactly the v1 constraints: required keys, types, enums, numeric ranges, `#rrggbb` patterns. Returns *all* errors, never throws. |
| `normalizeProfile(profile)` | applies the schema `default`s, filters `layers[]` to valid roles, **never mutates** the input, and is **idempotent**. |
| `profileToSettings(profile)` | maps `global` onto the generator settings surface (`style, strokeCount, strokeSize, detailLevel, styleStrength, opacity, randomness, colorMode, pathOrder, multiLayer, …`). A profile with no `style` does **not** force one. |
| `profileToLayerStyles(profile)` | `layers[].style` (enabled roles only) → the `layerStyles` record Phase 2.2 consumes. `null` when nothing overrides → a no-op. |
| `profileToLayerProps(profile)` | `layers[].{opacity,blendMode,order,enabled}` → per-role panel props for `js/ui/layers.js`. |
| `applyProfile(profile)` | one call → `{settings, layerStyles, layerProps, mediaModel, multiLayer, seed, valid, errors}`. |
| `profileFromSettings(settings, overrides)` | the inverse — build a schema-valid profile from engine settings (export / round-trip / Phase 5 seeding). |

The validator is deliberately a **subset** (no remote `$ref` resolution, no AJV);
schema §5 already prescribes swapping it for vendored LAYERS AJV schemas. The
`validateProfile` signature survives that swap unchanged, so callers do not move.

## 3. Engine wiring — `engine.generate({ profile })`

`PaintingEngine.generate()` now expands `opts.profile` (or a previously-set
`settings.profile`) **before** it reads its own settings, so:

- the profile's global block sets style / count / detail / opacity / order / etc.;
- its `seed` is used when `opts.seed` is absent;
- its per-layer styles drive Phase 2.2's `layerStyles`; its media model is carried;
- **an explicit `opts.*` still wins** (profile is the fallback, not the master).

No profile present → the branch is skipped entirely and output is unchanged.

## 4. Evidence

- **Unit tests:** `node tests/engine.test.js` → **84/84** (11 new profile tests:
  validation accept/reject/flag, normalisation + idempotence + no-mutation,
  settings mapping, layer-style/layer-prop mapping, `applyProfile`, round-trip,
  role/enum consistency).
- **Behaviour probe (real headless Chromium, the app's engine path):**
  `node scripts/profile-probe.cjs` → **PASS** — the profile's style drives the
  render (`style=watercolor` → registry `watercolour`), the profile **seed** is
  used (two seeds → different pixels), the same profile **re-bakes to identical
  pixels**, `opts.style` overrides the profile, and per-layer overrides land on
  the right band (`highlights → pastel`, `background → ink`).
- **Visual baselines:** `node scripts/visual-regression.cjs` → **9/9** unmoved
  (the profile branch is inert without a profile).

The probe caught a real bug on first run: `normalizeProfile` was not idempotent
when `mediaModel` was absent (it produced `null`, which then crashed a second
pass). Fixed and pinned with an idempotence unit test — the class of bug a pure
unit test on the module alone would have missed.

## 6. Honest assessment / next

- 4.1 is the **engine side**. The user-facing surface — save / load / browse a
  profile library — is **4.2** (a UI stream, Mac candidate). Until 4.2 lands, a
  profile reaches the engine programmatically (`generate({ profile })`); there is
  no control in `controls.js` yet, which the feature bar requires before calling
  the *feature* user-visible.
- `effects[]` is validated and round-tripped but **not yet applied** at render
  time — that is renderer work (Phase 6 polish), unchanged here and not claimed.
- `global.palette` / `colorMode: 'palette'` are carried into settings but the
  generator does not yet consume a user palette — noted, not claimed.
- Natural follower: **H1** (Phase 5) — `score(profile, image)` builds directly on
  `applyProfile` + the parity bench, and is the primitive the AI loop needs.

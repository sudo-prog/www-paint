## 1. Goal

Harness **H5**: *"agent proposes engine-code changes; benchmark gates; human
approves; algorithm improves over sessions."*

Tier B lets an agent change the **engine code itself**. The safety mechanism is
the rule from `AI_STYLE_HARNESS.md` §2: **nothing is kept unless the metrics
improve without regressing other images** — and a code change additionally needs
**human approval** (guardrail #4). This module is the deterministic engine-side
core that decision runs on.

## 2. Design — `js/engine/gate.js` (new, pure, node-testable)

| Export | Role |
|---|---|
| `GATE_DEFAULTS` | the policy: `objective`, `minGain`, `maxRegressions`, `regressionTolerance`, `approve`. |
| `evaluateSet(evalFn, images, opts)` | run one candidate over a benchmark → per-image metrics + `{mean, min, count}` on the objective. |
| `gateChange(baseline, candidate, opts)` | the decision: `keep` / `revert` / `pending`, with `improved`, `regressions`, per-image `deltas`, and `reasons`. |
| `gateVariants(baseFn, candFn, images, opts)` | evaluate a baseline and a candidate over the same set and gate — the one-call form. |

Decision order (first match wins):

1. mean objective did **not** improve beyond `minGain` → **revert**;
2. more than `maxRegressions` images regressed → **revert**;
3. otherwise, if not `approve`d → **pending** (metrics passed, human needed);
4. else → **keep**.

The gate is deliberately **proposer-agnostic**: it knows nothing about *how* a
variant is produced, so the same core gates a knob change, a code patch, or a
different renderer. "Human approval" is an explicit input (`opts.approve`); the
gate never auto-approves.

# P2.5 — Media panel: the front door for wet / ink / tonal parameters

**Stream:** M2 · **Owner:** Mac/FE (Hermes) · **Date:** 2026-11-11
**Modules:** `js/ui/media.js` (NEW) · `js/ui/media-host.js` (NEW)
`js/engine/brush-media.js` · `js/engine/masks.js` · `js/engine/wetsim.js` (consumers, unchanged)
`js/ui/layers.js` · `css/style.css` · `index.html` (additive)
**Interface:** IF-1 / IF-2 consumers only — no engine signature changed

---

## 1. Why this note exists

The three engine modules had **zero UI**. Their parameters were unreachable:
`grep` for `bleed|tide|granulation|wetness|tonal` in `js/ui/` returned nothing.
`js/ui/controls.js` is ThinkPad-owned (HANDOFF §6), so the fix could not be a
section bolted onto that panel.

**Decision: a sibling surface, not a shared-file edit.** The media panel is its
own `aside.panel--media` with its own strip / head / rail chrome, built by a
Mac-owned module. The ThinkPad-owned `controls.js` and `app.js` are never
imported or edited. The one host integration point is a Mac-owned shim
(`media-host.js`) that patches the `window.__app` instance the host already
exposes — the ThinkPad can fold those calls into `App._init()` later and delete
the shim.

## 2. What was built

### 2.1 `js/ui/media.js` — `MediaPanel`

Three sections, one per engine module. Every value dispatches
`media-settings-change` with `{ section, key, value, settings }`.

| Section | Engine module | Controls |
|---|---|---|
| **WET MEDIA** | `wetsim.js` (IF-2) | `maxWet` · `dryRate` · `flowRate` · `heightScale` · `granulation` + **Seed Reset** |
| **MEDIA** | `brush-media.js` | `bleed` · `bleedOpacity` · `tideDarken` · `granulation` · `granulationCount` |
| **TONAL MASKS** | `masks.js` (IF-1) | 4 band toggles · `lo` · `hi` · `softness` · `backgroundThreshold` · composite preview |

Parameter ranges/defaults are **read from the engine schemas**, not retyped:
`MEDIA_PARAMS` from `brush-media.js`, and `DEFAULT_LO/HI/SOFTNESS` from
`masks.js`' default export. The panel opens showing the engine's own
out-of-the-box values, so it is output-neutral until a consumer opts in.

### 2.2 `js/ui/media-host.js` — the shim

- builds the panel against `#media-root`
- adds `app.toggleMediaMode()` (the Media nav button calls it)
- stores settings on `app.engine.settings.{wetSim,media,masks}`
- computes the tonal-mask composite after an image is analysed
  (`loadImageFile` is wrapped once, guarded by `__mediaHostPatched`)

### 2.3 Shell (index.html)

- `<aside class="panel panel--media" id="media-root">` with strip / head / rail
- a **Media** nav button (`#btn-media-mode`)
- import-map entries for the two new modules + the three engine modules

### 2.4 CSS

`.media-*` rules use the **same primitives** as the controls panel (section
titles, slider rows, hints) so the two panels read as one system. Dark theme
gets its own overrides for track/border contrast.

---

## 3. Behaviour

**Desktop.** The media panel is hidden until Media mode is on. Toggling Media
swaps the left rail: brush controls leave, media panel takes the slot. The panel
collapses to the 56px icon rail like the other two.

**Mobile (≤768px).** The panel is a `position: fixed` overlay, closed on load,
opened by either the Media nav button or the floating toggle (which
`index.html` routes to the media panel while media mode is on).

**Mask preview.** `setMaskPreview()` accepts an RGBA buffer or `ImageData` plus
optional coverage; the panel only displays what a consumer computed — the
engine boundary stays one-way. The note line shows live coverage percentages,
and toggling a band filters that list immediately.

## 7. Not done (deliberately)

- **The parameters are not yet consumed by the render path.** The panel stores
  and dispatches them; `wetsim.js` / `brush-media.js` do not read them during
  a stroke. That is the Phase 3 / 2.2 consumer work, and it is ThinkPad-owned
  (`painter.js`, `renderer.js`). The UI is the front door; the engine plumbing
  is the next stream.
- **No per-style media presets in the UI.** `setMediaPreset()` exists on the
  panel and `MEDIA_PRESETS` is imported, but no control calls it yet.

## 8. M6b re-verification (2026-11-12) — two real defects found and fixed

The §7 claim ("the parameters are not yet consumed by the render path") was
**imprecise**. The ThinkPad landed the render path (B1: `renderer.setWetMedia`
driven by `settings.mediaModel`). The actual gap was one missing mapping, and
there was a second, independent defect in the mask preview.

### 8.1 Defect 11 — the panel was an inert settings shell

`media-host.js` stored the WET MEDIA section at `engine.settings.wetSim`, but
`engine.generate()` reads **only** `engine.settings.mediaModel`
(`engine.js` → `mediaModelToWetOpts`). Nothing mapped between them, so **no**
media-panel control changed rendered output.

Evidence (same image + seed, real headless Chromium):

| step | meanLum | bytes |
|---|---|---|
| dry (no `mediaModel`) | 245.00 | 2373 |
| `engine.settings.mediaModel={kind:"wet",…}` | 110.60 | 56638 |
| panel Wetness slider → max | **110.60** | **56638** |

The engine path worked; the panel path did not.

**Fix.** `media-host.js` now builds a schema-valid `mediaModel` from the panel's
`wetSim`/`media` sections (`mediaModelFromPanel()`), clamped to the frozen
`$defs/mediaModel` ranges, and writes it to `engine.settings.mediaModel` on
every wet/media change and on attach.

**Output-neutrality (HANDOFF §2 rule 5).** The panel's display defaults are
`wetsim.js`'s own defaults (`maxWet 1.5`), which describe a *working* wet sim —
mapping them naively switched wet media on for every user who never touched a
control. A non-UI `wetOptIn` flag (carried in `WET_SIM_KEYS`, deliberately kept
out of `WET_SIM_PARAMS` so no slider is rendered) is set on the first wet
control move. While false the model is `{kind:"dry"}`, which
`mediaModelToWetOpts` maps to `null` → **byte-identical output**.

### 8.2 Defect 12 — mask band toggles changed nothing

`masksCompositeRGBA()` ignored the band flags entirely and always composited all
four bands, so a band toggle could not change the preview.

**Fix.** `masksCompositeRGBA(masks, w, h, bands)` takes optional per-band enable
flags (omitted → historical all-enabled behaviour, so existing callers are
unaffected), and `media-host.js` passes `settings.bands`.

> **Probe pitfall (worth remembering):** the first version of the verification
> image was a smooth gradient with **zero background coverage**, so toggling the
> background band was *correctly* a no-op and the probe reported a false
> "toggle does nothing". A band toggle can only be verified on an image that
> actually has that band. The shipped probe now uses an image with a flat dark
> background (background coverage 0.506).

### 9.4 Defect 13 — the band toggles had no `id` and no `aria-label`

`js/ui/media.js` created the four tonal-band buttons with a class and
`data-band`, but **no `id`** — they were the only controls in the panel without
one, so no id-based automation could target them and the panel's own id
convention was broken. They did carry text content, so they were not unnamed in
the accessibility tree, but they were untargetable.

**Fix:** `btn.id = media-masks-band-<key>` plus `aria-label = <label>`, matching
the sliders' `media-<section>-<key>` convention. The band row still fits on one
line at 390px and 1440px (re-audited).

### 9.5 Maestro's limits (what it cannot do here)

- **No `sliderInput` command in web mode** — an attempt to drive a slider that
  way fails with `Invalid Command: sliderInput`. Sliders are driven from the page
  with synthetic `input`/`change` events instead.
- **`assertWithAI` / `assertNoDefectsWithAI` need `MAESTRO_CLOUD_API_KEY`** — not
  available, so AI visual assertions are unavailable.
- **`runScript` and `evalScript` have separate scopes** and neither exposes
  `window`; `globalThis` works in `evalScript`. A top-level `await` is rejected.
- **It asserts the accessibility tree, not pixels** — so "does this control change
  the output?" is out of scope. That half is `scripts/media-panel-probe.cjs`,
  which hashes the exported PNG before/after (see §8.3).

### 9.8 A note on the dev server (worth remembering)

Two `python3 -m http.server 8099` processes were already running from the repo
root (one bound `127.0.0.1`, one `0.0.0.0`, started 2026-11-03 and 2026-11-11).
Starting a third failed with `OSError: [Errno 48] Address already in use` — which
looks like a server failure but is not.

`http.server` reads files from disk **per request**, so a long-running server
still serves the latest edits; it does not hold a stale snapshot. Verified by
hashing the served bytes against disk after the test run:

```
js/ui/media.js        served=366445bc20 disk=366445bc20 MATCH
js/ui/media-host.js   served=5a30fdbc74 disk=5a30fdbc74 MATCH
js/engine/masks.js    served=fd5587cf40 disk=fd5587cf40 MATCH
```

Lesson: check `lsof -nP -iTCP:8099 -sTCP:LISTEN` before assuming a server
needs starting, and verify the served bytes rather than trusting a start command.

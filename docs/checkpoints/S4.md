# Checkpoint S4 — explicit hierarchical passes in the Style Profile

**Date:** 2026-11-14 · Agent: BE (ThinkPad) · Track S item **S4**
(`docs/TRACK_S.md` §3).
**Status:** done. A profile can now author its paint schedule as first-class,
tunable passes (`bg → masses → edges → accents`); a profile with no `passes`
produces **byte-identical** output, proved by the 9 pinned visual baselines.

---

## 1. The item

> **S4 — Explicit hierarchical passes in the Style Profile** — `passes: [{ id,
> scale: coarse|medium|fine, layers: [...], ... }]`, mapped onto the existing R2
> multi-scale machinery (residual drives the next pass).
> *Exit criteria:* Profile can express bg→masses→edges→accents as first-class,
> tunable steps; absent `passes` = current behaviour, byte-identical.

Before S4 the engine's schedule was **interpolated, not authored**: R2's
`buildScalePlan` derives three passes from `scales`, `coarseRadius`,
`fineRadius`, `coarseBlur`, `fineElongation` and `weightBias`. A profile could
tune those *numbers* but could not say *which step paints what*. S4 makes the
schedule a first-class part of the portable object — the difference between a
profile being a parameter set and being a **procedure**.

### 2.1 The pass object

```json
{ "id": "accents", "scale": "fine", "layers": ["highlights"],
  "radius": 0.64, "blur": 0, "elongation": 1.6, "weight": 1, "alpha": 0.9, "detail": 0.7 }
```

`id` is required (a pass is addressed by name); everything else is optional.
`scale` picks the pass's dab radius, reference blur and elongation strength from
the **same** coarse→fine interpolation `buildScalePlan` uses; `radius` / `blur` /
`elongation` override any of them per pass; `alpha` / `detail` override the
global dab opacity / detail response; `weight` is a **ratio** (the plan's weights
are normalised to sum to 1, exactly as `buildScalePlan` does).

### 2.2 Where the two schedules meet — one code path

`resolvePassPlan(opts, baseR)` is the single seam:

```js
if (!Array.isArray(passes) || passes.length === 0) return buildScalePlan(opts, baseR);
```

so `optimise()` has no second schedule and the default is *provably* untouched —
pinned by a test that asserts `resolvePassPlan(opts, baseR)` **deep-equals**
`buildScalePlan(opts, baseR)` when no passes are given.

### 2.3 Band bias — a bias, never a gate

A pass that names `layers` (tonal roles) gets its residual **anchoring** weighted
by a per-pixel mask:

```
score(i) = err(i) · (1 − spread·cov(i)) · mask(i)      // was: without mask(i)
```

- Roles resolve through the same soft masks the layer system renders with
  (`masks.js` IF-1): `background|shadows|midtone|highlights` → the four tonal
  bands (`midtone` → `midtones`); `outline` reads the analyser's own edge field.
  Several roles combine by `max`, so a pass can span bands.
- The mask is normalised to `[0.05, 1]` — a **soft bias, not a hard cut**. That
  floor is deliberate and measured: once a band is satisfied its residual falls
  below the floor-scaled residual elsewhere, so the pass **falls back to the
  global residual instead of idling**. The pass stays residual-driven at all
  times; the band only decides *where the residual is looked for first*.
- Band masks are built **only** when some pass declares layers — a geometric or
  plain explicit schedule computes nothing and changes nothing.

### 2.4 The profile → engine wiring

A profile's `passes` reach the optimiser through the existing Score mapping:

```
profile.passes[]  →  profileToOptimiserOptions()  →  optimiser.passes  →  resolvePassPlan()
```

No new consumer, no new code path: `scoreProfile` / `scoreProfileStyle` (and
therefore the H2 search and the H5 gate) honour a profile's explicit schedule the
moment the profile declares one, and are untouched when it does not.

## 3. Tests (all structural, node-only, no DOM)

| Test | Pins |
|---|---|
| `no explicit schedule → the geometric plan runs verbatim` | `resolvePassPlan == buildScalePlan` for absent **and** `[]`; `OPTIMISER_DEFAULTS.passes === null` |
| `an absent explicit schedule leaves the output byte-identical` | `optimise(…, {passes:null})` and `{passes:[]}` emit the **same shape list** as no option at all |
| `an explicit plan maps scale onto radii/blur/elongation and normalises weights` | order preserved; `coarse`→`coarseRadius`, `fine`→`fineRadius`, `medium`→midpoint; `blurR` = `coarseBlur·baseR` coarse → `0` fine; `3:2:1` normalises to `½:⅓:⅙`, sum 1 |
| `explicit radius/blur/elongation/alpha/detail override the scale keyword` | every numeric override wins |
| `an explicit schedule still emits exactly the budget, deterministically` | same seed → identical shapes; `count` exact; `stats.scales` = schedule length; error still falls; every shape valid |
| `a band-scoped pass anchors in its band, an unscoped one does not` | 3-band synthetic image: highlights-scoped >90 % in the bright third, shadows-scoped >90 % dark, midtone-scoped >85 % mid, and an **unscoped** pass scores ≥0.2 lower on the band |
| `profile validation accepts a well-formed pass, rejects a bad one` | `passes[0].scale` / `.layers` / `.id` / `.alpha` / `passes` are the paths reported; a pass-less profile stays valid |
| `normaliseProfile defaults a bare pass and is idempotent` | a bare pass → `{id, scale:'medium', layers:[]}`; an id-less pass is dropped; `normalize(normalize(x))` is a fixed point |
| `a profile without passes sets no optimiser option` | `profileToPasses` → `null`; `'passes' in profileToOptimiserOptions(bare) === false`; with passes it is carried through verbatim |

**No test asserts a fidelity gain.** Per the Track R rule, a synthetic image may
only back *structural* assertions; every fidelity claim belongs to the parity
bench. S4 makes no fidelity claim — it makes the schedule expressible.

### 4.1 Measured band behaviour (scratch probe, not committed)

A 96×96 image of three vertical bands — dark `[25,25,25]` | mid `[128,128,128]` |
bright `[235,235,235]` — single fine pass, `count: 90`, `seed: 5`,
`regionInit: false`, classified by the emitted stroke's centre third:

```
band=highlights  n=90  dark 0   mid 0   bright 90   meanLum 235.0
band=midtone     n=90  dark 6   mid 84  bright 0    meanLum 124.3
band=shadows     n=90  dark 90  mid 0   bright 0    meanLum  22.8
band=outline     n=90  dark 52  mid 0   bright 38   meanLum 111.1
band=(unscoped)  n=90  dark 29  mid 0   bright 61   meanLum 166.5
```

The unscoped pass is itself biased toward the bright third on this target (the
mid band equals the flat background fill, so it carries no residual) — which is
why the test compares *against* an unscoped run rather than against 50 %.

## 5. What S4 does NOT do (recorded, not hidden)

- **No per-pass geometry other than the dab.** A pass tunes radius / blur /
  elongation / weight / alpha / detail and *where* it anchors; it cannot yet
  choose a different **shape type**, a different **style**, or a different
  **blend**. Stroke-language primitives are **S5**; the two compose (a pass is
  the natural place a primitive weight would hang), but S5 is not implied by S4.
- **The band bias consumes the tonal masks' own definition.** The `background`
  band is the *very dark paper* band (`masks.js` `backgroundThreshold`), not "the
  big flat region" — on a mid-grey-dominant image, `background` may be nearly
  empty. That is the existing IF-1 definition, reused deliberately rather than
  re-invented; a pass that wants "the flat area" should name `shadows` or
  `midtone` per that definition.
- **No UI.** `passes[]` is engine + schema only; the library UI (Mac, M10) does
  not yet surface or edit passes, and the H2 proposer does not emit them (it
  searches bounded scalar knobs). Both are follow-ups, not blockers.
- **No fidelity claim.** Whether an explicit `bg → masses → edges → accents`
  schedule *beats* the geometric plan on the parity bench is an open measurement
  (and S10's matrix is where it belongs). S4 ships the expressibility with the
  default path provably unchanged.

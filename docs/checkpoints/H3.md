## 1. Goal

Harness **H3**: *"vision → profile from 1–4 refs; iterate on metrics + critique.
≥70% usable first proposals (roadmap 5.1)."*

The flagship half of the AI loop: a **vision LLM** proposes a Style Profile from
reference images; the H1 metrics + H2 search then refine it (the metrics are the
critique), and H4 memory records the attempt.

## 2. Design — `js/engine/vision-propose.js` (new, node-only)

The **LLM backend is injected** (`opts.llm`, async `({system,user,images}) =>
string`), so the orchestration is deterministic and testable with a stub — no
network in tests.

| Export | Role |
|---|---|
| `buildProposalPrompt(opts)` | the `(system, user)` prompt describing the **bounded** action space, generated from `KNOB_SET` (so it can never drift from the real knobs). |
| `parseProposal(text)` | tolerant parse: a bare object, a ```` ```json ```` fence, or JSON embedded in prose; accepts `{knobs}`/`{global}`/flat; every value goes through `clampKnobs`. Returns `null` when nothing usable. |
| `proposeFromImages(images, opts)` | the step: LLM → parse → **refine** (`searchProfile`, seeded) → score (`scoreProfile`) → optional `memory.record()`. An **unusable proposal falls back** to the base profile's own knobs (`ok:false`) instead of crashing. |
| `openAICompatibleBackend(cfg)` | a real adapter: an OpenAI-compatible `/chat/completions` call with `image_url` parts (dependency-free `fetch`; the caller supplies the key — nothing here stores one). |

Guardrails honoured: determinism (seeded refinement + a stub gives identical
output), bounded space (`clampKnobs`), every attempt recorded (H4).

## 5. Honest scope — what is NOT claimed

- **The ≥70%-usable-first-proposals criterion is NOT measured here.** No vision
  backend is configured in this environment (the local gateway requires a key,
  which is out of scope), so the real-LLM run is **pending**. The check runs the
  real adapter only when `H3_BASE_URL` + `H3_MODEL` (+ `H3_IMAGE`) are set; the
  mechanism and adapter are in place for that run.
- The prompt asks one round; the **multi-round** critique loop (render → compare
  → re-prompt) is orchestration above this module and is not built here.
- The browser-side wiring (calling the backend from the app with a user key) is
  a Phase-5 UI concern, not engine code.

**Therefore H3 is `mechanism done; real-LLM validation pending`** — not `done`.
